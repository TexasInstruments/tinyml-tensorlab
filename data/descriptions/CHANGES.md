# description_timeseries.json (2026.08.13 release) → descriptions.json — handoff notes

Old file: `2026.08.13/description_timeseries.json` (v1.4.0, timeseries-only, flat dict)
New file: `tinyml-modelmaker/data/descriptions/descriptions.json` (v1.5.0, combined, keyed by target module)
Companion file: `overrides.json` (this handoff — see "What to do with overrides.json" below)

Format change: old file's top-level keys are now nested one level deeper, under a
target-module key. What used to be `old['model_descriptions']` is now

folder — regenerated after the §1 contamination fix, so its numbers match this doc.

## 1. Cross-module data contamination — found and fixed during this handoff

Not part of the original ask, found while investigating why `radar`'s `model_descriptions`
included ~39 clearly timeseries-named models (`CLS_1k_NPU`, `ArcFault_model_*`, etc.)
instead of just its one real model (`Pose_and_Fall_model`), and why `radar`'s device
list included the entire C2000/MSP catalog instead of just `IWRL6432`.

**Root cause 1 — model registry leak, both directions:**
`tinyml_modelmaker/ai_modules/{timeseries,radar}/training/tinyml_tinyverse/{timeseries_classification,radar_classification}.py`
both import `get_model_descriptions()` directly from the shared
`tinyml_modelzoo.model_descriptions.classification` registry and re-export it unfiltered.
`tinyml_modelzoo/model_descriptions/_base.py:36-48`'s `task_type` filter parameter is a
documented no-op (`"not currently used but available for future"`) — the only real
filter is a flat `enabled_models_list` that mixes every module's model names together.
Result: `radar`'s `_model_descriptions` registry picked up all of timeseries's models,
and `timeseries`'s registry picked up radar's `Pose_and_Fall_model`.
**Fixed**: added a `common.task_type`-based whitelist filter at each module's own
registry-population boundary (`radar/training/__init__.py`, `timeseries/training/__init__.py`)
— shared modelzoo code untouched, so this doesn't affect anything else that consumes it.

**Root cause 2 — hardcoded device/preset lists:**
`radar/constants.py`'s `TARGET_DEVICES` was a literal copy of timeseries's full device
list with `IWRL6432` appended, and `PRESET_DESCRIPTIONS` had entries for 12 non-radar
devices (7 empty placeholder scaffolding, 5 with real MSPM0/MSPM33 compilation configs
of unconfirmed intent). No filtering logic was involved — just wrong constants.
**Fixed**: trimmed both to `IWRL6432` only, per your explicit call to remove the MSP
entries too rather than keep them pending confirmation.

**Effect on numbers used elsewhere in this doc**: this fix changes what §5's "genuinely
new models" list actually is (see below) — the earlier raw diff included
`Pose_and_Fall_model` as a "new timeseries model" because it was contamination, not a
real addition. Verified post-fix: `radar.model_descriptions` = `{'Pose_and_Fall_model'}`
only, `radar.target_device_descriptions` = `['IWRL6432']` only,
`radar.preset_descriptions` = `{'IWRL6432'}` only, zero collisions with `timeseries`
in any of the three sections.

## 2. Content removed on purpose this release — now in `overrides.json`

Two top-level sections (`context_help`, `help_url`) were generated by dead backend
code — nothing in tinyml-modelmaker or tinyml-mlbackend's Python read them, only the
description-generator wrote them. The Python functions that produced them have been
deleted from the codebase. If your GUI still renders anything from `context_help`
(capture/livedemo help-link panels) or `help_url`, pull it from `overrides.json`
going forward — this content will **not** be regenerated by future runs unless
someone re-adds the functions.

- `context_help` — per-task_type help-doc links for capture/livedemo/train/compile screens.
- `help_url` — single string, `"file://help.md"`.

## 4. Real regression: `target_device_descriptions` lost all per-device metadata

**Not GUI-only, not part of this cleanup — pre-existing bug in current codebase.**
(Distinct from §1's radar contamination — this is about `timeseries`'s own device
metadata disappearing, not about wrong devices leaking in from another module.)

- Old: dict of 27 devices, each `{device_name, device_type, device_selection_factor,
  device_details, sdk_version, sdk_release}`.
- New: flat list of 31 bare device-name strings. No metadata field survives anywhere.
- Confirmed root cause: `tinyml_modelmaker/ai_modules/timeseries/constants.py`'s
  `TARGET_DEVICES` is now just `[TARGET_DEVICE_F280013, ...]` — a list of name
  strings. The rich dict form doesn't exist anywhere in the current codebase; it
  can't be regenerated even by re-running the generator.
- Confirmed **not** a training-pipeline bug: `timeseries_base.py:699` now reads a
  static `training.target_device_flash_kb` model property (see §6) instead of
  looking up `flash_size_kb` from this dict, so training itself is unaffected.
- **`MSPM33C34` is gone entirely** — not even present as a bare name in the new
  list. Either intentionally deprecated or an accidental drop; not confirmed either
  way — flag to the device/constants owner.
- 5 device names are new and have **zero** metadata available anywhere (they don't
  exist in the old file either, so there's nothing to override with):
  `F28002x`, `F2807x`, `F2837xS`, `F2838x`, `F28P551x`.
- The old rich dict is preserved wholesale in `overrides.json` under
  `timeseries.target_device_metadata` — deliberately **not** named
  `target_device_descriptions` to avoid a shape collision with the new file's
  same-named key (dict vs. list). Cross-reference by device name; don't blind-merge.
- Same root cause visible in prose: `help_descriptions` shrank from 8667 to 5140
  chars because the entire "Supported target devices" section (per-device product
  links + SDK release) was dropped. Diff in `diff_report.json['help_descriptions']`.

## What to do with `overrides.json`

`overrides.json` is a transition artifact — its shape mirrors `descriptions.json`
(nested by target module). To reconstruct the equivalent of what you used to
receive:

```python
merged = json.load(open('descriptions.json'))['timeseries']
overrides = json.load(open('overrides.json'))['timeseries']
merged.update(overrides)  # adds back context_help, help_url, training_module_descriptions,
                           # live_capture*, live_preview*, target_device_metadata
```

Ownership going forward: this file is a snapshot of 2026.08.13 content, frozen — it
will not be regenerated or kept in sync with future modelmaker releases. Your team
owns deciding whether to keep consuming it as-is, drop the features it backs, or
push for the underlying getters to be reimplemented upstream (recommended
especially for §4, the device-metadata regression).
